# Stage 8 — MySQL integration (opt-in)

Stage 8 retains the Stage 7 JavaFX UI/services and adds an opt-in MySQL storage
backend and one-time CSV importer. **CSV is still the default**. Data is NOT
silently migrated. This is a compatibility migration, not a production booking system.

## Requirements
- JDK 21, Maven, MySQL Server 8.0+
- Back up the `database` folder and your MySQL database first.
- Run `sql/schema.sql` in MySQL Workbench (or CLI) to create the tables.
- Create a separate MySQL user with SELECT, INSERT, UPDATE, DELETE privileges.

## PowerShell — example settings (replace username and password)
```powershell
$env:CINEMA_STORAGE = "mysql"
$env:CINEMA_DB_URL = "jdbc:mysql://localhost:3306/cinema_booking?useUnicode=true&characterEncoding=UTF-8"
$env:CINEMA_DB_USER = "cinema_app"
$env:CINEMA_DB_PASSWORD = "YOUR_PASSWORD"
```
These apply only to the current terminal session, not to the entire PC.

## Import existing CSV once
```powershell
mvn -q compile exec:java -Dexec.mainClass=com.cinema.ImportCsvToMySql
```
The importer uses the `database` folder in your current working directory and
imports in dependency order. It uses upserts without removing existing rows.
It will fail if existing CSV data violate table constraints. Fix the source data
or relational references rather than disabling FK checks. For non-empty databases,
make a full backup before import. Run the importer once against an empty schema
for the clearest results. It does not atomically import all 9 tables.

## Start app in MySQL mode
```powershell
mvn clean javafx:run
```
After verification, SQL `SELECT COUNT(*)` from all nine tables should match the
CSV record counts. If you close this terminal or unset the variables, JavaFX
will use original CSV files again.

## Known limitations / next steps
- Existing service/repository API is retained; each repository save updates its
  entire table in one SQL transaction, not just one changed entity.
- Booking and ticket saves use **separate transactions**; multiple clients and
  failures between saves remain unsafe. Do not deploy concurrent ticket sales
  until a database-first transaction with seat locking is implemented.
- Existing passwords are plaintext (legacy), not secure for production.
- IDs are still generated by Java services, not MySQL AUTO_INCREMENT.
- CSV fields containing commas were not escaped in the original project and
  cannot be reliably imported without cleaning.
- Changing SQL-mode data does not update CSV backups.
- Start terminal from project root, which contains `pom.xml` and `database`.

## Issue detected in the bundled legacy data
The included `rooms.csv` has Room IDs **4, 5, 6** referring to **cinema_id=2**,
but `cinemas.csv` has no Cinema ID 2. The importer will reject those rooms
under the foreign key constraint. Before importing, decide whether to restore
Cinema ID 2 from a trusted backup, or reassign those rooms to the correct
existing cinema. **Do not change IDs at random**. Make the repair in a *copy*
of the CSV database first, verify it, then rerun import against an empty schema.
